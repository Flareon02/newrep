# Отчёт о релиз-кандидате: сервер 4.4.0 + расширение 8.2.1

Ветка `refactor/production-hardening`. В `main` ничего не вливалось, production не затрагивался.

> **Главное, простыми словами.**
> Код проверен автоматическими тестами и в настоящем браузере (Chromium) против имитации серверов-источников.
> **Проверка на вашем staging-сервере НЕ выполнена**: у облачной сессии, в которой я работаю, нет доступа к вашему
> VPS по SSH (из неё наружу открыт только HTTPS через прокси). Поэтому всё, что требует реального сервера, —
> реальные источники (Fonbet, GGBET, Pinnacle, HLTV…), ограничение памяти через systemd, soak на сутки,
> реальный рост диска — **не проверено**. Это «кандидат», а не «готов к production».
> Все цифры ниже — с моей тестовой машины и на синтетических данных. Они показывают поведение кода,
> но **не заменяют** замеры на staging.

Обозначения статусов: `VERIFIED E2E` — проверено в настоящем браузере с настоящим сервером;
`VERIFIED AUTOMATED` — проверено автотестами; `STATIC ONLY` — только чтение кода; `NOT VERIFIED` — не проверялось.

## 2. Какие реальные внешние источники работают

**Ни один не проверен.** Из моего окружения Fonbet, GGBET, Pinnacle, AstekBet и HLTV отвечают 403 или недоступны,
а к staging у меня нет доступа. Я не имитирую успех: статус каждого источника — `NOT VERIFIED`.

Что проверено вместо этого: при любом сбое источника (п. 1, 12 режимов) сервер не падает, сохраняет последние данные,
не повторяет запросы лавиной и сам восстанавливается. Это поведение кода, а не доказательство, что реальный источник
сейчас отдаёт данные. После запуска на staging источники проверяются командой `node tools/feed-report.mjs` (она уже готова).

## 6. RAM в простое

Локально, синтетика: холодный старт на пустой БД — **105–115 МиБ RSS**, куча ≈13 МиБ (`docs/PERFORMANCE-BUDGET.md`).
С большой БД (700 тыс. строк истории, файл SQLite ≈430 МиБ) старт: **≈160–180 МиБ**.
**На staging не замерено.**

## 7. RAM в штатном режиме

Локально, мок AstekBet: 12 LIVE-матчей — **≈113 МиБ в среднем, пик 136 МиБ**.
Умеренная нагрузка (60 LIVE, 600 линия, 3 SSE-клиента, БД с 700 тыс. строк): **среднее 211 МиБ, пик 250 МиБ**.
Только Astek работал, остальные три источника в моке недоступны, то есть реальная нагрузка выше.
**На staging не замерено.**

## 8. Пиковая RAM

- Нагрузка «занято» (120 LIVE, 1200 линия, 10 SSE-клиентов, счёт меняется при каждом опросе, БД 700 тыс. строк):
  **среднее 253 МиБ, пик 288 МиБ**.
- Расчёт коэффициентов HLTV: **211 МиБ** (до расчёта 141).
- Запас против лимита контейнера 768 МиБ и против 1 ГиБ машины есть, **но** это без трёх остальных источников
  и без ограничения cgroup (п. 14).

## 9. CPU

Локально: штатный режим ≈1,2 % ядра (пик 3,3 %); умеренная нагрузка ≈5–7 % (пик 42–52 %);
«занято» ≈17 % в среднем, пики до 114 % (задержка event loop до 118 мс).
Искусственный предел: 200 LIVE-матчей с изменением на каждом опросе дают ≈57 % среднего CPU и паузы event loop ≈1 с —
реальных ленточных объёмов такого размера мы не видели, но это граница для одного ядра.
**На staging (1 ядро, реальные источники) не замерено.**

## 10. Размер БД

Измерено только на синтетике: ≈215 байт на строку журнала коэффициентов; 700 тыс. строк истории — файл SQLite ≈420–430 МиБ.
Реальный размер БД вашего production и staging **неизвестен мне**.

## 11. Рост БД

**Не измерен.** Он зависит от числа матчей и частоты смены коэффициентов в реальных лентах, а они мне недоступны.
Прогноз из локального 20-минутного прогона **недействителен**: он целиком состоит из начального заполнения
(файл рос с 417 до 434 МиБ за посев данных, а не за счёт работы), поэтому цифры «1,1 ГиБ в сутки» из
`docs/evidence/local-soak-20min-report.json` нельзя использовать. Единственное достоверное число — ≈215 байт на строку журнала.
Реальный прирост даёт только soak на staging (`esports-monitor-soak.service` уже подготовлен, п. 15).

## 12. Рост логов

Журнал Docker ограничен конфигурацией (`local`, 10 МиБ × 3 = **максимум 30 МиБ**); для systemd на staging журнал
ограничен настройками journald, которые ставит `provision.sh`. На уровне `info` штатные опросы не пишутся,
повторяющиеся строки схлопываются. Реальный темп роста на staging не замерен.

## 13. Прогноз диска

**Не может быть дан честно без данных staging.** Что известно: каждая строка журнала ≈215 байт; хранение истории
ограничено 1 годом / 100 000 строк на снимок; журналы коэффициентов и счёта по умолчанию **не ограничены**
(retention выключен); логи ≤ 30 МиБ. Что нужно: 1–3 суток soak на staging, затем
`node tools/soak-report.mjs` выдаст прогноз на 1/30/90/365 суток по реальному приросту. Диск 10 ГБ на production
остаётся под вопросом именно из-за неограниченных журналов; при прогнозе, не укладывающемся в год,
включать `ODDS_RETENTION_DAYS` (механизм проверен тестами, защищает матчи, которые ещё в ленте).

## 14. Тест с ограничениями production-профиля 1 ГБ

**Не выполнен**: нужен systemd с cgroup на staging (`MemoryMax`, `MemorySwapMax=0`, `CPUQuota`), в моей среде systemd нет.
Скрипт готов: `ops/staging/profile.sh prod` ограничивает **только службу приложения**, а не всю виртуальную машину,
поэтому SSH не пострадает. Косвенно: пик локально 288 МиБ при куче, ограниченной 320 МиБ; потолок из бюджета —
768 МиБ на контейнер. Подтверждения под реальным давлением памяти нет.

## 15. Результат soak

Выполнен **только локальный 20-минутный прогон** (80 замеров, умеренный профиль, синтетические данные), это проверка
отсутствия быстрых утечек, а не soak:

- RSS: среднее 235, p95 270, максимум 285 МиБ; кучa 29–64 МиБ; тренда роста нет (RSS на последнем замере 231 против 238 в начале).
- История в памяти: **≈14,8 тыс. строк при 700 тыс. сохранённых** — и не растёт.
- Дескрипторы 25–45, потоки 9–11, без роста. Ошибок матчера и таймаутов: 0.
- Event loop: макс. 333 мс (первый замер при старте), в среднем 120 мс.
- CPU: среднее 5 %, p95 13 %, максимум 42 %.

Полноценный soak (минимум 24 ч с реальными источниками) **не выполнен**. Запуск на staging подготовлен
(`systemctl start esports-monitor-soak`, затем `node tools/soak-report.mjs`), результаты сохраняются сами в JSONL.

## 17. Оставшиеся риски

1. **Реальные источники не проверены**: нет подтверждения, что ленты работают на staging; окружение с VPS может иметь другие IP-репутации/блокировки.
2. **Память под давлением и cgroup не проверены**; три из четырёх источников не участвовали в замерах.
3. **Диск**: журналы коэффициентов/счёта без ограничения; прогноз неизвестен.
4. **CPU на одном ядре**: при сотнях активных LIVE-событий с постоянными изменениями возможны секундные паузы (синтетика).
5. **`publicHistory(0)`** на 100 тыс. строк ≈ 0,55 с — разовая тяжёлая выборка полной истории.
6. **Без TLS**: токен идёт открытым текстом по HTTP; рекомендован обратный прокси (описан в `DEPLOYMENT.md`).
7. **Контейнер работает от root** (с жёсткими ограничениями) — не менялось, чтобы не сломать права на существующие данные.
8. **Токен записи общий**, а не по пользователям — сознательно, без сложной системы авторизации.
9. Часть интерфейса расширения проверена только чтением кода (п. 4); часть вообще не проверена (п. 5).
10. Расширение хранит токен в `chrome.storage`; не в Git (есть тест).

## 18. Технически готов ли код к развёртыванию в production?

**Нет — пока нельзя утверждать.** Код — релиз-кандидат: автотесты проходят, браузерные сценарии на моке проходят,
поведение при сбоях источников корректно. Но критичные для production пункты не проверены: реальные ленты,
память и CPU под ограничением 1 ГБ / 1 ядро, прогноз диска и многочасовая стабильность. Формулировку «готов» можно
использовать только после пунктов ниже.

## 19. Что нужно сделать до production

1. **Дать мне доступ к staging** (см. сообщение с результатами: рекомендуемый вариант — запустить Claude Code прямо на staging VPS;
   приватный ключ в чат вставлять не нужно).
2. Выполнить `ops/staging/provision.sh` (Node 22, пользователь `monitor`, `.env` с самостоятельно сгенерированным `API_TOKEN`,
   systemd, ротация журнала, ufw — SSH первым) и `esports-monitor-deploy` (проверка `/health` и автоматический откат).
3. `tools/staging-auth-check.mjs`: чтение открыто; запись без токена → 401, с неверным → 401, с верным → 200.
4. `tools/feed-report.mjs`: зафиксировать, какие реальные источники работают с этого IP, какие нет (без подмены результата).
5. Собрать тестовое расширение для staging: `node tools/build-staging-extension.mjs` (токен подставляется при сборке, в Git не попадает) и пройти ручную проверку п. 4–5 (особенно E06, запрос разрешения для адреса, уведомления ОС).
6. `ops/staging/profile.sh prod` — замеры под лимитом службы (RAM текущая/пиковая, CPU, диск, БД, логи): простой, штатно, live, расчёт коэффициентов, SSE-клиенты, загрузка истории, запись в БД, retention, перезапуск, несколько клиентов.
7. Запустить soak ≥ 24–72 ч, затем `soak-report`; получить прогноз диска на 30/90/365 суток; решить, нужен ли `ODDS_RETENTION_DAYS`.
8. Каждую найденную ошибку: воспроизвести → тест → исправить → полный набор → staging → повтор E2E → отдельный коммит.
9. Обновить этот отчёт реальными числами и только тогда пересмотреть п. 18.
10. Включить TLS (обратный прокси) перед использованием токена через интернет.
11. Для production: резервная копия БД, `API_TOKEN` (новый, не staging), план отката (`rollback`), и только по вашей команде.
